## 结合你的简历，LIMA 应该怎么聊

你最适合重点讲的是：你怎么把一个可疑的 C/C++ 内存问题查清楚。开场先说负责的模块，再拿实际案例展开。数据库、队列和前端放到架构追问里。

这个选择和你的简历有关：LIMA 里写的是 C/C++ 分层检测、独立执行环境和 Agent 流程；技能里写了 RAII、智能指针、CMake、Clang、ASan/GDB；个人总结又明确希望深入客户端安全和软件保护。面试官很可能顺着这些内容问对象生命周期、崩溃根因、构建环境和复现可信度。

几段经历可以这样衔接：Web 靶场让你接触漏洞复现和调用链分析，OGVul 让你研究模型怎样结合源码证据判断漏洞，LIMA 则把重点放到真实仓库的分析、构建和验证。工业软件逆向经历可以补充你阅读陌生代码和梳理模块关系的经验。它们是相关经历，不要说成同一个系统或同一套实现。

## 面试官说“介绍一下 LIMA”，先说这一段

“LIMA 是我和几个同学一起开发的开源多智能体漏洞检测项目。我主要做 C/C++ 内存漏洞检测，包括越界读写、UAF 和 Double Free。整个项目有前端、主服务和负责分析的 Docker 容器。用户通过前端提交任务、看报告，前端通过 HTTP 和主服务通信。主服务负责准备代码，再安排工具和 Agent 去分析。Agent 生成 PoC 后，主服务里的编排程序会通过工具接口，把编译和运行交给独立的 Docker 容器。

用的时候，可以选已经导入的本地仓库，也可以提交 GitHub 仓库和版本。LIMA 会先固定这次要看的代码，列出能读取的文件，确定要分析哪些 C/C++ 源码。开启的基础分析工具会先跑一遍。到了 Agent 这一步，系统会尝试从程序分析结果里找线索；如果没有候选，就让 Discovery 直接读源码，找值得继续看的地方。

拿到线索以后，Scout 先筛一遍，再让 Specialist 具体分析：这里可能是什么漏洞，什么情况下会触发，然后生成 PoC。环境能编译运行的话，LIMA 就自动跑一下，看 ASan 报错的位置和类型，跟前面的判断能不能对上。如果没触发漏洞点的话，就让 Critic 看看是判断有问题，还是 PoC 要改。调用次数和重试轮数都有上限。最后报告里会写清楚发现了什么、跑出了什么结果、还有哪些没确认。我拿到报告后，再自己手动复现一遍，看真实应用里能不能触发，会造成什么影响。

另外，运行环境这块我也参与了。因为要编译别人的代码，还要跑模型生成的 PoC，所以我把这些操作放在独立的 Docker 容器里，限制它能访问哪些文件、能开多少进程，以及占用多少资源。哪一步没跑成功，报告里也会记下来，方便我后面复现时排查。

比如 ResInsight 里有一个处理双孔模型时的堆越界写，我可以具体讲讲它为什么出错，以及我后来怎么手动复现的。”

说到最后一句时，你应当已经准备好一个能深入讲的案例。这里的“负责”和“参与”沿用简历范围；具体哪个函数、哪条测试、哪次定位是你完成的，要用自己的提交和记录补充，不能把整个仓库的能力都算作个人工作。

## LIMA 的整体架构怎么讲

这一节用于回答“整个项目怎么组织”。先交代自己的开发范围，再讲模块之间的关系：

“整体架构我可以简单介绍一下，我主要负责里面的 C/C++ 检测模块。用户可以从页面或者 API 提交仓库扫描，平台另外还有 PR 审查入口。主服务先检查权限、创建任务、准备代码，再安排对应的分析，最后把报告保存下来，展示到页面上。

C/C++ 这边，主服务负责把代码和工具结果准备给模型，安排 Agent 分析。Agent 生成 PoC 后，编排程序调用复现工具，把它交给独立的 Docker 容器去编译、运行，再把结果带回分析流程。这个工具底层也是通过 HTTP 调用容器里的分析服务，所以“Agent 使用工具”和“服务之间通过 HTTP 通信”说的是不同层面的事。代码快照会带一个哈希，再加上文件路径和工具运行记录，保证前后分析的是同一份代码。

Agent 和基础工具的结果最后会放到同一份报告里，但会写清楚结果从哪里来、验证到了哪一步。模型认为有问题、静态工具报了问题、实际运行触发了问题，这几件事会分开记录。我主要负责这条 C/C++ 分析流程，前端、任务存储和其他语言的扫描由其他部分处理。”

如果对方只想知道技术栈，再补一句：平台后端用 Python，前端用 React；本地可以用 SQLite，部署时可使用 PostgreSQL 和 Redis。这里的“C/C++ 模块”指分析对象是 C/C++，编排和分析器接入代码主要仍是 Python。

## C/C++ 多智能体怎么运行检测

这一节用于回答“Agent 实际是怎么一步步工作的”。可以这样说：

“仓库准备好以后，先确定这次看哪些源码。如果已经有线索，就可以直接交给 Agent；没有的话，程序会先试着从分析结果里生成候选。这一步目前主要做 UAF：用 Clang 解析代码，找出内存在哪分配、在哪释放、指针指向哪里、后面又在哪里使用。如果没有生成候选，就让 Discovery 把源码分成几段来看，自己找可疑位置。不过 Agent 不只分析 UAF，也会看越界读写、重复释放这些问题。

然后 Scout 把线索筛一遍，看看哪些值得往下查。选出来以后，Specialist 再看对应的代码，说明可能是什么漏洞、要满足什么条件、怎么走到出错的位置，还有哪些前提没确认，同时写出用于实验的 PoC 驱动。

环境准备好了，程序就把驱动和目标源码交给独立的 Docker 容器，自动编译，再跑 ASan。触发了预期的错误，就往下检查证据；没触发、又还有重试机会的话，就让 Critic 看假设和运行记录。它可以指出假设有问题，也可以改一下驱动，再交回去跑。重试轮数、调用次数和输出大小都会限制住。

最后由程序按规则判断验证到了哪一步，会一起看程序分析结果、工具证据和模型意见。证据对不上的，就留给人工复核。自动实验还会检查：是不是真跑起来以后报的错，错误类型对不对，崩溃是不是发生在目标文件里。如果只是驱动自己写错了、自己崩了，不能算目标项目的漏洞。

前面这些由 LIMA 自动做。我拿到结果后，再自己手动复现，看从真实应用入口能不能触发，输入和调用方式合不合理，以及实际会有什么影响。”

追问时需要保留三个细节：Discovery 是无事实候选时的回退路径；首次实验命中后可以不再调用 Critic；不同角色主要由程序传递有界上下文，不等于每个角色都能自由搜索整个仓库。具体配置接线和覆盖上限见后面的“当前实现还需要说清的边界”。

如果被问“是否只用了 Clang，是否只支持 UAF”，要区分三件事：

- 基础工具链使用 Semgrep、Clang Static Analyzer 和 ASan，覆盖越界读写、UAF 和重复释放。
- Agent 当前复用的结构化事实提取与确定性候选生成，主要是 UAF 专项。这些事实描述代码行为，不是已经确认的漏洞；Clang AST 解析与 Clang Static Analyzer 告警也是两条不同路径。
- Discovery/Specialist 的内存漏洞类型包包含 UAF、重复释放、越界读写、空指针解引用及整数溢出相关问题，但类型包能提出假设，不等于所有类别都有同等成熟的事实提取和动态确认能力。当前没有实现与 UAF 同等的、覆盖所有类别的统一事实候选生成器。

另外，当前回退是在整批没有事实候选时才触发。如果已有 UAF 事实候选，不会因此自动再做一次完整的 Discovery 来寻找所有其他类型。所以不能把“支持多种漏洞假设”说成“每次都全面扫描了所有漏洞类型”。

## 自动检测和个人工作怎么区分

这里有两件不同的事：你开发检测模块，以及你使用模块后的人工验证。介绍开发贡献时，讲你实现的分析器接入、Agent 编排、证据校验、隔离和预算；介绍一次实际扫描时，说明检测链由 LIMA 执行，结果出来以后再由你手动复现和核查。不要把系统自动做的每一步都说成自己逐个手工分析。

目前代码也包括自动复现，所以不能把它说成“LIMA 只分析，PoC 全由我来跑”。更准确的说法是：

“我负责开发 C/C++ 自动检测模块。扫描时，LIMA 自己筛线索、分析代码，环境允许的话还会生成并运行 PoC。我主要是在它出结果以后，再手动复现一遍，确认真实应用里能不能触发、影响是什么。”

自动运行依赖模型、独立的 Docker 容器、构建依赖和预算。具备自动执行链不等于每个仓库都能无人干预地完成确认：缺依赖、实验失败或证据不足时，系统会中止、降级或保留待复核状态。人工复现也不只是重复一条命令，还包括核对输入是否合法、故障是否来自原项目、真实入口是否可达。以每个案例的实际人工操作为准。

当前实现的边界：平台保留基础工具链与 Agent 链。服务端先执行已开启的基础工具分析，再运行 Agent 链并合并结果。Agent 线索优先使用调用方提供的 leads；没有 leads 时尝试从 Clang UAF 事实生成候选；仍无候选才调用 Discovery 直接读源码。Semgrep 告警没有直接作为这段 Scout 线索生成的输入，基础工具结果主要作为后续辅助证据。因此可以说“Agent 主导，支持直接源码发现”，但不能说服务端已经完全取消静态分析依赖。

## 真实案例：ResInsight 双孔模型的堆越界写

建议主讲这个案例。它能把文件输入、数组大小、下标计算、ASan 日志和真实应用复现串起来。选择它是因为证据和根因适合展开，不是因为已经证明它能造成最严重的攻击效果。

### 可以直接接在项目介绍后面说

“比如我们在 ResInsight 里发现过一个堆越界写。它是做油气数据可视化的软件，这个问题出在导入双孔模型的时候，处理的是文件里的 PORV 数据，也就是孔隙体积数据。

这段代码会把数据数量除以二，再按这个数量创建一个 `vector<int>`。但后面的循环还是会处理全部数据，处理到后半部分时，再减去前面的数量，映射回数组下标。它漏掉了数量是奇数的情况。

比如文件里有 11 个正值，除以二以后是 5，所以数组只有 5 个元素，合法下标是 0 到 4。循环走到最后一个值时，它的下标是 10，再减去 5，得到的还是 5，刚好超出数组一个元素。出问题的地方是一个 `+=`，所以这里会发生越界读改写。

归档里的 ASan 复现用的是真实 INIT 文件，读回来以后调用原项目的处理函数。日志报的是 heap-buffer-overflow，位置就在这个 `+=` 上。数组分配了 20 字节，报错地址恰好在这 20 字节后面，和前面的下标计算能对上。

我后来又从真实应用入口手动复现，使用配套的 EGRID 和 INIT 文件，在界面里导入。这次用的是 13 个 PORV 值，还是同样的奇数问题。应用能把案例导进去，当场没有崩溃。所以我会分开说：ASan 实验证明了这里有越界访问，界面复现说明这组文件能从真实入口进入相应处理流程。不能因为界面没崩，就说没有问题，也不能反过来说已经证明能执行任意代码。

后来维护者加了下标检查，映射后的下标如果超出数组范围就跳过，也补了奇数数量的回归测试。按保存下来的修复记录，这个补丁已经合进主线。这个例子里，我主要想讲清楚的是：自动分析和实验给出的结果，还需要结合真实入口手动确认，才能把问题和影响说准确。”

### 如果对方只让你简短举例

“比如 ResInsight 导入双孔模型时有一个 off-by-one。文件里 11 个 PORV 值，代码按 11 除以 2，只分配 5 个 int，但最后一次循环算出了下标 5，超出合法范围 0 到 4。ASan 在原项目处理函数里报了堆越界，地址正好是 20 字节数组的末尾之后。我又在 GUI 里导入同类文件确认真实入口可以走到这段处理流程。上游后来加了下标检查和回归测试。”

### 这个案例最容易被追问的地方

**为什么日志报 READ，你却说是越界写？**

“因为出错语句是 `+=`，它要先读原来的值，再写回去。ASan 在读这一步就拦住了，所以日志先报 READ。按源码分析，这条语句是越界读改写，不能把日志描述成已经记录到 WRITE。”

**为什么用 11 个值做 ASan，界面里又换成 13 个？**

“这是两次不同的实验。11 和 13 都是奇数，都能让最后一个下标等于数组长度。ASan 那次是 11 除以 2 得到 5；GUI 那次是 13 除以 2 得到 6，最后的下标是 12 减 6，仍然超出一个元素。不能把两次实验的输入和现象混着讲。”

**是不是整数溢出？**

“不是，这里没有整数超过类型范围。问题是整数除法向下取整以后，数组大小和后续循环的下标计算对不上，是一个边界检查问题。”

**GUI 没崩，怎么说明危害？**

“越界访问不一定当场崩溃，普通构建和 ASan 构建的内存布局、检查方式也不一样。我能明确说的是，生产函数的 ASan 实验确认了越界，GUI 导入确认了真实入口能进入这个流程。至于是否覆盖了特定堆元数据、能不能进一步利用，还需要另外的观测和验证。”

**是全程 LIMA 自动跑出来的吗？**

“要按这次实验留下来的记录区分。LIMA 当前有自动分析、生成驱动和执行实验的能力，但这个历史案例里哪些步骤自动完成、哪些步骤人工补过，不能只看现在的平台能力倒推。我可以分别讲归档里的驱动实验，以及我后来做的真实应用复现。”

## 其他真实漏洞也可以按这个顺序讲

优先准备两个案例：一个根因和复现路径很清楚的成功案例，一个最终被排除或没有完成确认的案例。前者说明分析能力，后者说明你知道什么时候不能下结论。

下面是练习用的填空，不是已经发生的项目事实。方括号要用自己的记录替换：

“我拿［公开仓库和固定版本］里的一个问题来说吧，出问题的是［模块或函数］，它本来是用来［用途］的。

最开始，LIMA 的［工具或 Agent］发现了［线索］，分析后认为问题可能出在［根因假设和证据］。按报告里的判断，只要［触发条件］，就会出现［具体错误操作］。我后来手动复现时，检查了［实际核查内容］，主要是确认有没有［反例或错误调用］这种情况。

LIMA 当时自动跑出来的结果是［实际状态：运行命中、未命中或未完成］。我自己复现用的是［构建配置和输入］，从［驱动或真实应用入口］进去，看到的是［实际结果］。然后我又对照了［栈或边界计算］，检查是不是同一个原因。

这个问题现在是［已提交、维护者确认、补丁合并或已分配编号］。其中［步骤］是工具或者模型完成的，我自己做的是［步骤］。”

如果测过修复版本，可以补上同样输入在修复前后的结果。说清驱动实验和真实应用复现各自做了什么，不要把两次验证合成一次。

UAF 案例至少讲清：对象在哪里创建、哪个操作结束了它的生命周期、后面谁持有旧引用、什么条件下再次访问，以及为什么不是重新绑定后的新对象。越界案例则讲清实际分配大小、索引或拷贝长度从哪里来、边界检查为什么没挡住。

ASan 崩溃还需要结合 API 使用约定和真实可达路径解释。要核对崩溃是否发生在原项目、是否需要不合理地修改目标代码。当前 `experiment_matches_target` 会检查实验阶段、错误类型和故障文件，并排除故障落在 driver 文件的情况；这些检查仍不能代替人工确认安全影响。

## 简历里的 ResInsight 成果怎么说

新版简历已经把笼统数量换成 ResInsight 及其 roffcpp 组件的 5 项问题。面试时对方会想知道这些问题怎么统计，以及你本人做到了哪一步。

“这五项是［团队或个人，按实际情况填］统计的。我最熟悉的是［案例］，可以把它的复现过程完整讲一下。最开始是［工具或模型］找到线索，后面通过［人工分析和实验］确认。至于维护者有没有确认、补丁有没有合并，我是按每个问题收到的实际回复来记录的。”

维护者确认、接受修复、补丁合并、提交编号申请和编号已分配，是不同的状态。如果只有确认回复，就说到确认回复，不要提前承诺最终会分配 CVE。确认 bug 也不一定等于确认安全漏洞。

面试前自己备一张清单，每条记录固定版本、问题根因、复现输入、人工参与部分、披露记录和当前状态。未公开细节不必放进这个开源仓库的文档，面试时选择可以公开的案例。

## 针对这份简历，最可能问的问题

先练个人工作和真实案例，再补原理和工程细节。

### 1. 项目是你独立做的吗？和同学怎么分工？

说明团队项目和个人范围。准备一个自己负责模块的提交或 PR，再说它与别人模块之间的接口。不要用“我们实现了全部功能”回避个人贡献。

### 2. 最有代表性的一个漏洞是什么？能现场讲根因吗？

先讲正常功能和触发条件，再讲错误操作、反例和验证，最后说外部反馈。开头不必介绍整个平台。

### 3. 漏洞是你发现的，还是模型发现的？

按真实过程拆开：谁提出线索、谁定位根因、谁写 PoC、谁完成版本对照和披露。模型发现线索、人工确认也是可以清楚描述的成果。

### 4. 这五项问题怎么去重？依赖库问题算几次？

准备根因、受影响组件和触发路径等去重依据。一个问题影响多个版本，不直接按版本数算成多个漏洞；崩溃样例数也不等于独立漏洞数。

### 5. 维护者确认了什么？CVE 到哪一步了？

按问题逐条回答，只说有记录的状态。确认 bug、确认安全影响、补丁合并和分配 CVE 要分清。

### 6. 怎样排除错误调用接口导致的崩溃？

说明正常调用约定、攻击者可控输入和可达路径，再解释有没有绕过必要初始化或人为制造错误状态。无法证明可达性时保留这个限制。

### 7. Semgrep、Clang Static Analyzer、ASan 各能证明什么？

Semgrep 提供规则候选；Clang Static Analyzer 结合编译上下文做静态路径分析；ASan 检查实际执行到的内存访问。静态分析不是执行，单次实验也不覆盖全部路径。

### 8. 为什么需要编译参数？`compile_commands.json` 是什么？

它记录翻译单元的编译命令、工作目录等信息。宏定义、头文件路径和语言标准会影响实际解析的代码。编译失败要区分环境缺失、源码问题和分析器限制。

### 9. UAF 和 Double Free 有什么区别？

UAF 是生命周期结束后继续使用；Double Free 是重复释放。继续准备别名指针、回调、容器失效和对象重新分配的例子，最好用自己案例中的对象解释。

### 10. 把指针设成 `nullptr` 能解决 UAF 吗？

只影响当前指针变量，其他别名仍可能悬空。需要看所有权和引用关系，不能只看一处置空。

### 11. 使用智能指针之后为什么还有内存问题？

准备讨论借出的裸指针、悬空引用、容器迭代器失效、并发访问和错误构造所有权。RAII 管理资源释放，不自动保证所有引用有效。

### 12. ASan 原理和盲区是什么？

至少掌握编译插桩、shadow memory、redzone 和释放后内存检查。它受执行覆盖影响，不能检测所有逻辑越界、并发问题和自定义分配器场景。

### 13. ASan 没触发怎么办？

检查是否成功编译、插桩是否生效、输入是否进入目标路径，再检查假设。可以调整复现，但不能把未触发直接写成已排除。

### 14. 整数溢出能靠 ASan 确认吗？

整数运算本身通常需要相应 UBSan 检查或确定性分析。整数溢出导致后续越界时，ASan 可能报越界，根因仍需分析。当前内存类型包包含 CWE-190，不代表每条调用链都有完整的运行时验证能力。

### 15. 大模型读哪些代码？能自己搜索整个仓库吗？

当前 C/C++ 链主要由程序准备上下文：Discovery 按翻译单元切窗读源码，Scout 读取线索周围的片段，Specialist 接收目标附近代码、匹配的事实和编译提示，Critic 再看假设与实验记录。不要说它已经可以任意搜索全仓、追踪所有跨文件调用；那会混淆其他 Agent 的工具循环和当前 C/C++ 的固定编排。服务入口还对翻译单元数量做了上限限制。

### 16. Scout、Specialist、Critic 各做什么？

Scout 筛选线索，Specialist 输出假设、触发路径、CWE、驱动、实验设计和未解决的前提。实验未命中且还可继续时，Critic 可以否定假设或修改驱动。首次实验命中后可以直接进入证据仲裁，不保证每个结果都再经过 Critic。角色更多本身不能证明准确率更高，需要对照实验支持。

### 17. 同一个模型扮演不同角色，意见一致可信吗？

不一定，同源模型可能犯同样的错。意见一致是分析参考，更高等级结论依靠与目标绑定的程序事实和动态证据。

### 18. 模型生成的 PoC 自己制造了越界怎么办？

检查故障位置和类型，再核对输入约定、分配和释放路径。driver 崩溃、随意更改目标逻辑或不成立的 API 用法，不能直接计作原项目漏洞。

### 19. 仓库注释里写“忽略之前指令”，怎么办？

源码和工具输出属于不可信输入。说明熟悉的上下文转义、严格输出契约和工具权限限制。仅靠一句提示词不够，也不能承诺完全防住注入。

### 20. 预算耗尽、超时、模型输出非法 JSON 怎么处理？

调用次数和 UTF-8 字节量由共享预算记账，响应大小、源码窗口与单次请求也有上限；这不是精确 Token 或费用统计。可修复的格式错误允许有限重试，身份契约错误不能靠重试换一个身份。模型失败和预算不足在 auto/required 下的处理不同；实验编译失败或没命中通常是分析结果，不直接等于任务失败。内核支持可选总 deadline，但当前服务入口没有传入该参数，不能说服务端已经按 `LIMA_CXX_AGENT_TIMEOUT_SECONDS` 限制整条 Agent 链。

### 21. Docker 里运行就安全吗？只读环境怎么编译？

Docker 需要与用户权限、文件访问、网络和进程限制配合。输入快照只读，编译产物写入受限临时工作区。继续准备 Landlock、seccomp、资源限制分别负责什么，以及能力不足时如何拒绝高风险执行。

### 22. 为什么运行 CMake 也有风险？

CMake configure 可以执行命令。说明管理员授权的构建配置和受信构建生成门禁，不能让模型或仓库内容随意设置执行权限。

### 23. 怎么测试误报？

用漏洞和安全对照样例检查具体边界，比如释放后重新赋值、不可达使用、正确长度检查。同时记录未执行和覆盖不足。fixture 不能代替外部项目评测。

### 24. 有证据证明 LLM 比纯工具好吗？

需要固定样本上的工具基线、工具加模型和不同 Agent 配置对照，并报告误报、漏报、耗时和费用。没有完成就说尚未量化；“找到五项问题”不能算准确率。

### 25. OGVul 和 LIMA 是什么关系？

“OGVul 更偏研究，主要看领域知识能不能帮助模型判断漏洞。LIMA 这边，我做的是实际仓库怎么分析、问题怎么验证。两边都会看源码证据，但具体实现和评测目标不一样。”OGVul 的 F1 和相对提升不能拿来作为 LIMA 指标，也不要暗示 LIMA 默认使用 OGVKG。

### 26. 简历里提到 MCP，LIMA 所有工具都走 MCP 吗？

主服务通过版本化 HTTP 接口调用独立的 Docker 容器里的 C/C++ 分析服务，不应统一叫 MCP。IDA + MCP 的逆向经历可以单独介绍，工具调用也不等于必须使用 MCP。

### 27. 这段经验对客户端安全有什么帮助？

“比如拿到不熟悉的 C/C++ 代码以后，怎么找输入、跟对象的生命周期、把调试环境搭起来，再查清楚为什么崩，这些经验在客户端分析里也用得上。不过 LIMA 主要看源码，二进制逆向和漏洞利用这部分，还得结合我另外做过的工作来讲。”再接实际做过的 IDA 分析。

### 28. 代码是不是 AI 写的？你怎么确认自己理解？

如实说明 AI 参与范围，选一个能逐行解释的模块，讲接口、关键判断、失败分支和测试。能解释为什么拒绝一条错误证据，通常比泛泛说“做了验收”更有说服力。

## 如果只讲 30 秒

“LIMA 是一个开源漏洞检测项目，我主要负责 C/C++ 这块。开启 Agent 后，它会自己分析代码、判断可能有什么问题，环境允许的话还会生成 PoC，编译运行，看 ASan 的结果。我参与开发的就是这套检测和验证流程，还有证据检查和 Docker 容器里的执行限制。报告出来以后，我再手动复现，确认真实应用里能不能触发。”

## 详细讲自己的检测流程

可以接着开场说，不必从 HTTP 请求、数据库和前端讲起：

“我这部分拿到的是固定版本的 C/C++ 代码，最后给出问题的位置、类型和验证结果。先固定版本，是为了保证模型看的代码、编译用的代码和报告对应得上。

现在服务端会跑基础工具分析，也会跑 Agent。Agent 可以用程序分析给出的线索；没有这类候选时，就让 Discovery 自己读源码找。基础工具报出来的问题也会留下来，不是每条告警都必须先让模型看过。

Scout 筛完线索，Specialist 再根据给它的代码和分析结果，判断可能是什么问题、怎么触发，并写驱动。像 UAF，就重点看对象什么时候释放、还有谁在引用；越界就看长度、索引和实际分配的大小。这些由 LIMA 自动分析，我不需要先把每个地方手工审查一遍。

环境能跑起来的话，LIMA 就把源码和驱动放到独立的 Docker 容器里，编译运行 ASan。没触发、还能继续试，就让 Critic 看记录，要不要改驱动再跑。第一次就触发了，就可以直接往下判断结果。这里会分清编译失败、正常退出和 ASan 报错，不能因为程序正常退出，就认为目标路径已经测过了。

程序会检查在哪个阶段出的错、错误类型对不对、是不是目标文件出了问题，再结合其他证据给出验证结果。证据对不上，就留给人工复核。我拿到报告以后，再从真实入口复现，看看调用方式合不合理、应用里到底能不能触发。”

Semgrep、Clang Static Analyzer 和 ASan 属于基础工具链；Clang 事实提取、UAF 证明和 ASan 实验也可以作为 Agent 的仪器。Clang Static Analyzer 的告警与 Clang AST/CFG 事实是不同输入，不要混讲。

## 别只说“接了三个工具”，还要解释你实现了什么

“我做的不只是把工具调起来。Agent 怎么拿到代码、怎么分析、怎么生成驱动，实验没跑出来以后怎么继续，这些都要接起来。工具这边也要准备构建信息，检查返回的结果是不是属于这份代码，以及调用次数用完了、编译失败了、模型返回的格式不对了，该怎么处理。具体我写了哪些，可以结合提交和测试讲。”

这段只保留实际属于你的工作。面试官继续问时，选一个自己熟悉的实现细节，例如：

- 独立的 Docker 容器返回的路径不属于当前仓库，或者行号超出文件范围时怎么处理。
- 构建失败以后为什么还能保留纯源码候选。
- PoC 崩溃落在 driver 里时为什么不能确认原项目漏洞。
- 安全样例已经重新绑定指针，怎样避免沿用旧的 UAF 假设。

每个细节最好能找到对应代码和测试，比把所有文件名念一遍更容易讲清。

## 分层检测，被追问时这样解释

“分层主要是看验证到了哪一步。只看源码、还没编译运行的，只能先算候选，也就是 candidate。用真实编译参数做了 Clang 路径分析，才可以标成 build-verified。基础工具链真正跑出了可信的 ASan 报告，再标成 confirmed。Agent 那条流程还有自己的状态，不能把两套标签混用，也不能只看模型说自己有多确定。

基础工具链主要看越界读写、UAF 和 Double Free。Agent 的类型包还包括其他内存问题，但能分析某种问题，不代表已经能把它完整地跑出来验证。比如整数溢出本身，就不能直接靠 ASan 判断。”

只要对方没有问到字段，不用主动背这些英文状态。

## Agent 和复现这部分可以重点展开

“我比较关注模型说这里有问题以后，接下来怎么确认。比如它说一个指针释放后还会被访问，那就要说明哪个对象、在哪里释放、在哪里用，以及什么情况下会走到这里。Critic 会去找反例，比如中间是不是重新赋值了，或者调用方其实已经限制了输入。

能做实验时，Specialist 会写出驱动，程序自动去编译运行。没触发的话，可以把记录给 Critic 看，再改驱动。编译失败可能是缺依赖，也可能是调用写错了，有些环境问题程序能识别，但不是都能自动修好。跑完没报错，也可能根本没走到目标分支。所以最后我还要自己复现，核对真实程序能不能走到这里、调用方式对不对。”

同一模型的几个角色不一定提供独立意见。多 Agent 是否比单 Agent 更有效，需要对照评测；可以先讲它怎样让分析过程可检查，不要直接宣称提高了多少准确率。

## 独立分析环境怎么讲

“这里要编译仓库里的代码，也要跑模型生成的驱动，所以我把这些操作放在独立的 Docker 容器里。源码保持只读，编译出来的文件写到临时目录。它能开多少进程、跑多久、用多少内存、输出多少内容，都会有限制，避免一个死循环或者异常程序一直占着资源。

另外，构建这一步本身也有风险，像 CMake 在配置时就能执行命令。所以不能让模型或者仓库随便给一段 Shell 就直接跑，要按服务端配置和权限检查来执行。”

如果被问到底层，再展开非 root、Landlock、seccomp、网络限制和能力不足时的拒绝行为。先理解自己实际用到的限制，再讲它们分别解决什么问题。

## 面试官问最难的地方，选一个展开

可以讲复现可信度：

“我觉得比较难的是，程序崩了，还得弄清楚是不是目标项目真的有问题。有时候是驱动写错了，有时候是单独调这个函数会崩，但真实应用根本走不到。所以我会把代码里的原因、驱动跑出来的结果和真实应用入口分开检查。ASan 报了错，也不代表就能直接当成这个应用的漏洞提交。”

也可以讲工具接入：

“还有一个麻烦的地方，是不同工具的结果不能直接混着看。编译成功不代表测试跑过，程序异常退出也不一定是内存错误。所以要分别记下工具有没有跑完、测到了哪里、有没有真正的漏洞证据。不能因为工具没跑起来，最后返回了空结果，就说没有漏洞。”

讲完判断方法，马上接一个自己处理过的实例。不要把整个平台所有难点都揽到个人经历里。

## 平台整体只需要准备这几句话

“平台还有 PR 审查、其他语言的扫描、任务管理和报告页面。我主要做 C/C++ 检测，拿到准备好的代码和配置后去分析，再把结果返回给主服务。Python 扫描、前端和存储不是我负责的，我主要了解它们怎么和我这部分配合。”

如果被问技术选型，可以补充平台使用 Python 后端、React 前端，以及数据库和异步任务。对于别人的模块，按实际了解程度回答，不需要替团队解释每个设计决定。

C/C++ 当前只检测、不自动修复。如果对方问平台修复能力，简要说明属于另一部分即可。

## 当前实现还需要说清的边界

- C/C++ Agent 当前接入完整仓库扫描；通用 PR 审查是另一条链，服务能力字段 `pull_request_scan=false`。内核支持 diff-only 参数不代表 PR 接入已经完成。
- 默认 `cxx_memory_mode` 和 `cxx_agent_mode` 都是 off，需要显式开启并配置模型及独立的 Docker 容器。不要把“不调用模型的本地规则模式”说成 C/C++ LLM Agent 仍在工作。
- 服务端当前只选取排序后最多 16 个 C/C++ 翻译单元。Discovery 还有文件字节数、总字节数和窗口数上限，不代表读完了整个大型仓库。
- `parallelism`、`dialogue_rounds`、`deadline_seconds` 在内核可以传入，但当前 `RepositoryScanner` 没有从服务配置传入它们。服务入口沿用内核默认值，不能把配置项存在说成已经生效。
- 预算类有 files/lines 字段，但当前主链明确记账的是 calls 和 bytes，另外靠固定窗口和读取上限限制上下文；不承诺每次读取都按 files/lines 扣费。
- 自动实验检查了故障文件和错误类型，但没有自动证明完整根因、外部可达性和利用价值。即使状态为 `runtime-confirmed`，人工复现仍有必要。
- `scripts/run_platform_evaluation.py` 的 fixture 路径使用模拟的分析服务和实验台，即使选择真实 LLM 也一样；实际 Clang/ASan 需要另外做真实容器实验。不能把这类通过等同于真实工具验证。
- C/C++ Finding 禁止自动修复；复现工具中的临时源码覆盖用于回归实验，不等于服务端已经自动生成并发布 C/C++ 补丁。

## 练习时按这个顺序
