# 修复信任前提加固（2026-11-09）

本轮针对 [全局审计中的两个 P1](LIMA_GLOBAL_REPAIR_TRUST_AUDIT_2026-11-09.md) 修改规划器、Oracle 和约束评测。此前相对根目录与自定义 SQL 包装器都可能获得 `verified-preview`，即使差分告警减少，漏洞仍然存在。

## 路径根目录

静态表达式现在必须具有绝对路径锚点。相对目录、`.`、盘符相对路径及动态拼接拒修；原有导入、唯一绑定、遮蔽和 helper 完整性检查继续生效。检查兼容 POSIX 和 Windows 的词法形式，生成的 helper 在当前运行平台调用 `is_absolute()` 后才执行 `resolve()`。因此其他平台的词法形式不会在运行时被悄悄解释成工作目录下的路径。

拒修意味着保留原始告警，不会替用户猜测部署根目录，也不会将原程序宣称为安全。并发文件系统修改造成的 TOCTOU 仍需要操作系统隔离或文件描述符相对打开机制处理。

## SQL 接收者

只对标准 `sqlite3.connect()` 创建的连接和默认游标提供参数化自动修复。证明从实际 `.execute()` 接收者追溯构造、唯一绑定和作用域，拒绝自定义 factory、包装器、参数接收者、重绑定、对象逃逸和动态命名空间。变量后缀、文件中的驱动导入、`sql-paramstyle` 注释均不能代替证明。

Oracle 在补丁 AST 上重新计算接收者证明；manifest 记录 `sqlite3-standard-v1`，但不能单靠该字段通过验证。参数占位符固定由已证明的驱动契约推导，而不是由 manifest 自选。SQL 结构、参数数量及差分复扫检查继续执行。

旧版 SQL manifest 缺少新驱动契约，或旧路径 helper 缺少绝对路径检查时，不能直接通过新版 Oracle，必须基于固定来源重新规划和验证；不对历史验证结果补写证明。

这会收窄此前基于导入猜测的 PostgreSQL/MySQL SQL 修复能力。它不影响 LIMA 自身的数据库存储功能。当前证明只处理受限源码构造，不覆盖外部模块篡改标准库等环境完整性问题。

端到端发布门禁测试改用真实内存 SQLite：正常值返回一条预期记录，`1 OR 1=1` 作为绑定值返回零条记录。测试客户端模拟远端发布，不会写入 GitHub。
