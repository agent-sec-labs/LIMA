# 修复发布门禁与隔离测试部署

`POST /v1/tasks/{id}/fix` 会创建远程分支、提交和 Draft PR。它要求租户的仓库修复授权，并且任务已经成功完成。

同一任务、来源、补丁和验证身份的重试会核对并复用同一次发布操作。结果尚未确认时返回 `repair-publication-pending` 和操作 ID，管理台提示重试同一任务；不将其显示为“未创建分支”。检测到发布记录或远端内容冲突时返回 `repair-publication-conflict`，停止后续写入。

## 固定来源

发布使用审计任务输入中保存的完整 40 位 head SHA，读取文件、下载归档和创建提交都绑定它。开始修复及写入前会分别比较当前 PR head；不一致时返回 `repair-source-stale`，不写 GitHub。缺少固定 SHA 的旧任务或手工 diff 任务需要重新通过固定提交的审计流程生成结果。

Webhook worker 从保存的 base/head SHA 通过 GitHub compare API 获取 diff，按配置限制响应字节数，内容和来源标记 `pinned-compare-v1` 一起持久化。无法获取该提交对时不回退到可变 PR URL。旧任务即使保存了 head SHA，只要缺少该来源证明，发布仍返回 `repair-source-unverified`，需要重新发起审阅；不能仅通过恢复旧 checkpoint 补出来源证明。

## 统一验证

所有拟发布文件都需要支持的修复 manifest。当前受限 CWE-22/78/89 修复走独立 AST Oracle 和全仓差分复扫；没有对应证明的旧 `REL-DEBUG-PRINT`、`SEC-HARDCODED-SECRET` 路径保留补丁规划能力，但不能发布。混合任务中的未修复项会保留拒绝原因。

CWE-78 目前仅支持标准 `echo` 和固定 `%s` 格式的 `printf` 数据参数；不将固定解释器加 `shell=False` 当作安全修复。未知程序、解释器、包装器、自定义可执行路径、额外位置参数和执行覆盖返回拒修，Oracle 从实际补丁重新检查这些约束。目标环境仍需保证标准程序的可信解析。

CWE-89 当前只支持可追溯至标准 `sqlite3.connect()`、无自定义 factory 的连接和默认游标；接收者必须具有唯一、可确认的构造绑定。参数接收者、包装器、别名逃逸、动态命名空间、重绑定和未知驱动均拒修。源码导入及 `sql-paramstyle` 注释不再提供证明。Oracle 从补丁 AST 重算驱动身份，并固定检查 SQLite 的 `?` 参数契约。PostgreSQL/MySQL 的业务存储支持不代表其漏洞自动修复已受支持。

CWE-22 的根目录需要静态绝对路径表达式及实际绑定证明；相对目录、`.`、盘符相对目录拒修，helper 在 `resolve()` 前检查当前平台的 `is_absolute()`，防止通过工作目录改变重定向根目录。只有同名全局变量或源码信任注释不够。参数遮蔽、重赋值、导入/删除/异常或模式匹配等重绑定、动态命名空间均可能使其拒修。当前证明采用保守子集，其他作用域内同名绑定也可能触发拒修。验证器同时检查实际根目录、helper 及其 `Path` 依赖的绑定，并对照固定 helper 规范，而不信任 manifest 自选的 helper。静态检查通过仍不能代替仓库测试或解决文件系统并发 TOCTOU。

发布还必须有配置的仓库测试命令、真实执行成功的 sandbox 回执，以及完整的编译、oracle、差分和测试检查清单。只有单个 `passed=true` 标志不够。草稿正文逐条列出实际检查，不会声明未运行的检查已经通过。管理台会区分“已创建”与“门禁阻断、未创建”。

修复归档在写入任何文件前检查全部条目头；符号链接、FIFO、设备等特殊类型或类型与目录名称不一致的条目会被拒绝。链接不被转换成普通文件，也不跟随链接复制内容。链接拒绝在验证检查中记录 `repair-archive-link-unsupported`，不启动仓库测试或创建提交。普通文件按 Git 的 `100644`/`100755` 模式记录；缺少 Unix 类型元数据的普通 ZIP 文件按非可执行文件处理。

模式通过独立的只读 JSON 元数据挂载传给测试容器，在一次性工作副本中恢复，避免 Windows 宿主的权限表示丢失执行位。发布前从固定父提交的 Git tree 逐级读取目标路径类型和模式；每次元数据读取有字节上限，截断、缺失、歧义或特殊条目在任何 POST 前拒绝，普通文件保留原模式。现有 sandbox 的 noexec 等执行限制继续适用，文件模式保留不等于目标平台原生 CLI 已完成实机验收。

## 下载预算与发布恢复

修复归档最多 64 MiB，以最多 64 KiB 的分块流式写入受控临时文件，再交给 ZIP 验证；不先将完整归档装入内存。Content-Length 仅用于提前拒绝，实际读取计数才是边界，缺失、虚报或分块响应也不能越过预算。上下文结束、读取/写入失败或验证异常都会清理临时文件。旧的 bytes 下载接口也有相同的默认大小上限。

修复源码 Contents JSON 上限为 1,000,000 字节，解码后的源码上限为 512 KiB；消费方在补丁规划和 AST 验证前再次检查。单次规划累计源码上限 20 MiB，最多 299 个修改文件；发布操作 JSON 记录上限 32 MiB。超预算返回 `repair-input-too-large`，不进入后续测试或发布。这些是单次操作预算，不代表全服务并发总配额。

服务初始化会新增 `repair_publications` 表，SQLite 与 PostgreSQL 共用操作协议。首次远程写入前，保存不可变意图、来源/补丁/manifest、验证命令、实际镜像和检查项身份。操作 ID 决定稳定分支名；随后记录已确认的 commit、PR 和最终结果。没有持久操作存储的直接调用不能发布。

重试仍须通过当前授权、来源和验证门禁。写请求的未知结果不再由 HTTP 客户端盲目重发；恢复会查询稳定 ref 和该分支的所有状态 PR，核对父提交、操作标记、完整树差异、修改 blob 和模式。未计划路径必须保持原 SHA，只有目标路径可改变。恢复不依赖大体积文本 diff。已完成操作的远端成果缺失或被修改时阻断，不自动重建或覆盖。

该协议恢复可见分支和 PR，不能承诺每个不可达 Git tree/commit 对象恰好创建一次；早期对象应答丢失后可能重建对象。它也不替代真实 GitHub 一致性、权限及故障恢复验收。来源已变更、权限被撤销或验证失败时仍阻断，不能借恢复流程跳过门禁；人工变更或持续未知状态需要核对已有操作。

## 隔离执行配置

在运行服务的执行节点配置：

```powershell
$env:LIMA_REPAIR_TEST_COMMAND = 'python -m unittest discover -s tests'
$env:LIMA_REPAIR_SANDBOX_IMAGE = 'registry.example/approved-repair@sha256:<approved-digest>'
$env:LIMA_REPAIR_VERIFY_TIMEOUT_SECONDS = '120'
```

镜像必须由管理员提前构建、安装目标项目所需的测试依赖并加载到本地 Docker，包含 `python3`；运行任务时不联网安装依赖。示例镜像名与摘要需要替换成真实批准值。配置命令按 Linux argv 解析，由容器中的固定 Python bootstrap 启动，不使用宿主 shell，也不继承宿主环境变量。

实际运行先将仓库输入复制到受控 staging，拒绝链接、不可读或超预算输入，并统一非 root 可读权限；不改变用户原目录权限。该输入只读挂载，容器在 tmpfs 中创建一次性工作副本。执行采用实际镜像 ID、禁止自动拉取、非 root 用户、只读容器根目录、禁网、删除所有 capability 和 no-new-privileges，并限制 CPU、内存、PID、输出及时间。超时会请求 stop/kill；未能确认停止时不能通过验证。报告记录镜像 ID、资源限制、执行与清理回执。

默认镜像为空，发布会被阻断。Docker 或镜像不可用同样失败，不存在宿主测试回退。标准只读 Compose 应用容器没有 Docker 执行通道，因此设置一个镜像名不会自动建立这项能力；可以在批准的宿主执行节点运行服务，或由部署方提供可信隔离执行适配器。不要通过给 Web 容器挂载 Docker socket 来省略执行边界。

## 上线验收

至少验证：成功的受限修复、测试失败、无镜像/无命令、初始 SHA 已变化、验证期间 SHA 变化、无 manifest、缺失 sandbox 回执、测试输出过量和超时清理失败。所有拒绝场景都不应创建 GitHub 提交或 PR。

本地静态 Repair Preview 不会执行仓库测试，也不直接发布。预览通过不能替代上述发布门禁。
