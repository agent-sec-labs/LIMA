# [Competition][E01][独立工具] 运行前只读检查，不启动模型或目标代码

## 目标和适合的执行者
让操作者在昂贵验证前确认案例、checkout、compdb 与 Sidecar 前提是否齐备。需要 Python CLI/JSON/Mock 测试能力，不需要判断漏洞。预计 1–2 天；范围仅单案例 preflight，不增加批量运行器。

## 当前可复用依据
只读参考 lima/openharmony_validation.py 的 load_openharmony_case、validate_case_checkouts、WorkspaceLimits、CheckoutPreflightError；lima/repository_import.py 的 RepositoryImportPolicy；lima/cxx_memory.py 的 CxxMemoryAnalyzerClient.health；scripts/run_openharmony_validation.py 的参数。不得调用 run_openharmony_validation / run_platform_review。

## 文件所有权
仅允许新增：
- scripts/preflight_competition_run.py（CLI）
- lima/competition_preflight.py（检查与输出投影）
- tests/test_competition_preflight.py
- docs/competition/tools/preflight.md
夹具全部在该测试临时目录中生成，不提交真实案例或修改共用 fixture。

## 输入输出合同
入口：python scripts/preflight_competition_run.py --case <case.json> --repository-import-root <root> --output <new-preflight.json> [--check-sidecar --analyzer-url <url>]。
1. 默认离线，复用现有 case/checkout 校验，保留既有预算和错误类别。检测 manifest、两个 checkout 固定 SHA/dirty/compdb/overlay、文件预算，既有校验失败不能降格为警告。不得 fetch/checkout/reset/build 或写被测目录。
2. Sidecar 健康探测是显式选项，只调用既有 health，使用有限超时且不重试。未选择时标 not-requested，不填 passed。URL 输入拒绝用户密码、query/fragment，输出不回显地址。
3. 检查模型配置只能记录是否提供必要项，不能发送认证/模型请求、读 .env 文件或输出实际凭证；缺配置不得声称供应商不可用，存在配置不得声称认证有效。
4. JSON v1：schema_version、checks[{name,status:pass|fail|not-requested,reason_code}]、prerequisites_passed、sidecar_requested、diagnostics。检查项失败后不伪造后续检查通过；结构/清单不可解析时记录错误并停止依赖检查。stdout 为简短同源摘要。
5. 退出 0=所有本次请求的前提检查通过；2=前提不满足；3=用法/输出错误。所有文字说明“前提通过不代表漏洞成立，也不代表模型已认证”。

## 验收矩阵
- AC1：正确案例前提通过；HEAD 漂移、dirty、缺 compdb、overlay 摘要错误、预算超限分别有稳定失败原因（可 Mock 已有校验器错误，接口复用有测试）。
- AC2：Mock 断言未调用模型/编译/执行；默认未请求 health；显式 health 超时不能通过。
- AC3：坏 manifest、输出已存在、缺输入、错误 URL、包含敏感文本的异常不会造成覆盖或泄漏。
- AC4：输入目录前后文件内容一致；两种演示的 JSON 和退出码对应。
