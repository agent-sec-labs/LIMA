# [Competition][E06][独立工具] 从已有证据包汇总多轮结果，保留失败和未知

## 目标和适合的执行者
把已有运行结果汇总成 CSV/Markdown，便于看清案例、版本、证据等级、失败原因和成本记录。只做数据搬运，不重跑、不重新判漏洞。需要 Python 文件处理/JSON/表格能力，预计 1–2 天。

## 当前依据
只读参考 lima/openharmony_validation.py 的 write_validation_bundle/_platform_document，以及 docs/COMPETITION_VALIDATION.md 对运行模式的区分。不要从本机 .zcode 或容器路径自动搜集数据。

## 文件所有权
仅允许新增 scripts/aggregate_competition_runs.py、lima/competition_run_summary.py、tests/test_competition_run_summary.py、docs/competition/tools/run-summary.md。测试自己生成小 JSON，不修改 writer 和共享夹具。

## 输入输出合同
入口：python scripts/aggregate_competition_runs.py --inputs <runs.json> --output-dir <new-directory>。
runs.json v1 含 runs 数组，每项显式给 run_label、bundle_dir，可选 performance_file、execution_label；run_label 唯一。允许绝对输入目录（这是本地 CLI），输出行只记录标签与相对证据引用，不披露宿主路径。
1. 只读输入 bundle 的 case.json/summary.json/两侧 platform.json；缺旧字段保留 null+原因，双侧不混用。坏包列 errors，不静默丢行。JSON 读取拒绝重复 key，关键字段冲突报错。
2. 一轮一行，记录 run_label、case_id、两侧 commit、validation_status、两侧 findings 按原 state 的计数、原 reason_codes、total_elapsed_seconds、已声明的运行模式、采样性能可选值及来源。执行/模型身份没有原始记录就 unknown；不要从 finding 状态推断模型真实/模拟。
3. CSV/Markdown 同源、排序稳定，不平均历史运行、不计算 precision/recall、不把多次 finding 相加称漏洞总数。同 case 不同 run 保留两行；输入路径重复/label 冲突具名拒绝，不能覆盖旧轮。
4. performance_file 可按 #292/PR #310 已声明的 schema_version=1 只读提取 wall_time_seconds/host.sampled_peak_rss_bytes 等已知字段；未提供或不兼容时 null+原因，不要求先合并 PR #310、不导入其代码。自有 Mock 构造最小数据。旧 bundle 完全可用，不依赖 #288/#293 或 E07。
5. 记录 summary 原始字节 SHA-256 用于定位这次读取的文件；必须注明未验完整 bundle，不使用 integrity_valid 字段，不重新实现已裁掉的 #288。
6. 输出 summary.csv、summary.md、errors.json；0=全部指定输入可解析，2=部分/全部输入错误且保留诊断，3=用法/输出冲突。CSV 单元格对以 =、+、-、@ 或制表符起始的自由文本做表格公式转义并在文档说明；Markdown 转义换行和竖线。
