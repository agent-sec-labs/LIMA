# [Competition][E14][独立工具] 正式报告材料缺件检查，只查字段和附件不判断漏洞

## 目标和适合的执行者
正式报告经常缺源码片段、PoC、版本依据或修复说明。本工具在组装前列缺件清单；只检查维护者填写的交付索引和附件，不用 LLM 理解 Markdown，不决定漏洞是否成立。需要 JSON/文件校验能力，预计 1–2 天。

## 文件所有权
仅允许新增 scripts/check_competition_report_materials.py、lima/competition_report_materials.py、tests/test_competition_report_materials.py、docs/competition/tools/report-materials.md、docs/competition/tools/report-materials.example.json。
只读参考赛题要求和当前 agent_report/openharmony_validation 输出；不改报告 writer、V4 schema、case 合同、已有 bundle 或打包 #299。

## 输入输出合同
入口：python scripts/check_competition_report_materials.py --index <materials.json> --root <approved-materials-root> --output <new-material-check.json>。
新增索引独立 schema_version=1、scope=report-materials-check、findings 数组。每项有唯一 finding_id；field_refs 包含以下八项相对附件路径：source_excerpt、description_and_cwe、trigger_and_path、poc_source、reproduction_instructions、impact_modules_and_versions、remediation、maintainer_review。一个正文文件可承载多项，但工具只声称引用存在且非空，不声称段落内容正确。
1. CVE 字段显式 cve_status=known|no-match-recorded|not-assessed；known 时要求符合格式的 cve_ids 和 evidence_ref；无对应记录保留状态，不自动标新漏洞。维护者复核项是显式附件/记录，只检查存在，不推断批准公开或签名真实性。
2. 附件必须落在显式 root 内的规范相对普通文件；拒绝绝对/盘符/../反斜杠、symlink/junction/reparse point、重复 JSON key。缺失/空文件逐条报告，不打开执行、不联网、不修改附件；大文件大小检查有预算，不把整个源码/PoC打印到报告。
3. 可选 severity 文本/执行记录引用由维护者提供；缺失标待补，不根据 evidence state/CWE/退出码计算严重度、稳定性或真实性。不能因附件名有 ASan 或 passed 而宣称漏洞通过。
4. 输出 schema_version、scope、case_label、fields_complete、per_finding_missing、input_errors、diagnostics，始终含 semantic_verification=not-performed、disclosure_approval=not-checked。0=结构/引用字段齐备，2=缺件或无效索引，3=用法/输出错误。fields_complete=true 不能显示“漏洞成立/可以公开/可以提交比赛”。
5. 这不是 #288 的完整性校验器，也不是 #299 的打包工具：不遍历所有包文件、不验 SHA 清单、不渲染 PDF、不执行敏感扫描、不生成 zip，不以此替代维护者终审。

## 队友人工检查
- [ ] 删除合成 PoC 附件，看到该 finding 明确缺 poc_source。
- [ ] 补齐文件后只显示“字段/附件齐备”，不显示“漏洞已通过”。
- [ ] CVE 未评估仍明确 not-assessed，不编造编号。
- [ ] 工具没有执行附件；PR 仅约定五个新文件。
