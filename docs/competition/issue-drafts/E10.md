# [Competition][E10] 参赛提交包组装与缺件清单（附 Codex 实施与人工验收清单）

## Problem to solve
作品提交（截止 2026-10-22）需要按官方要求组装材料：文档资料 PDF（≤10MB，含作品简介、设计方案、测试报告、其他文档、参赛作品声明）+ 可执行程序；命名规则"队长姓名+作品名称+资料名称"；正文不得体现学院、导师信息；模板见通知附件 2；须经培养单位资格审核后方可官网提交。目前没有可核对的提交清单与组装流程。本 Issue 先立任务书（10-15 前），执行窗口 **10-21**（组装+检查+模拟上传一轮完成）；**10-22 只处理提交系统问题，不再改材料**。

## 输入与依赖
- 材料内容定稿（作品简介、设计方案、测试报告、使用说明书/DEMO 脚本/正式漏洞报告）由维护者 10-20 后提供；本任务不写内容，只组装。
- 参赛作品声明模板：**需用户从官方通知附件 2 下载提供**（未到位时列入缺件清单，不阻塞其他项）。
- 可执行程序交付形态（源码包 / 镜像 / 两者）：**待用户 10-18 前拍板**。未定则停止最终组装并立即升级给用户处理，Codex 不得自行选择。
- 依赖：#290（环境示例，进程序包）、E08（部署验证）、#288（完整性校验器，复用于打包件校验）、E11 产物（视频，另列）。

## Proposed solution（Codex 实施）
1. 新增打包脚本（建议 `scripts/build_submission_package.py`）：从**显式 allowlist**（清单文件入库）打包源码、依赖/运行说明、维护者批准的正式漏洞报告、PoC/补丁/证据、文档 PDF、性能说明、声明、程序交付物；每项缺失输出缺件清单（哪项、谁负责、阻塞什么），不静默跳过。
2. 检查与命名：
   - 按"队长姓名+作品名称+资料名称"命名，报名字段（姓名/队名）走配置文件提供，不写死进仓库；
   - 逐项检查：PDF ≤10MB；正文无学院/导师字样（对 PDF 文本做关键词扫描，结果记录）；无密钥、无 `.env`、无本地数据库/缓存、无未批准漏洞材料、无 `.git`、无维护者本机绝对路径；
   - 输出全套 SHA-256 清单，复用 #288 校验器对打包件做离线完整性验证。
3. 模拟上传演练：把成品复制到独立目录模拟上传，再"下载"（复制回来）后打开复核——PDF 可打开、程序包可解压/可按运行说明启动到健康检查、清单与实物一一对应。10-21 完成一轮；发现问题当日修复重跑。
4. 不自动发布、不接触比赛平台；正式提交由用户执行。

### 文件范围
新增打包脚本、allowlist 清单模板、检查报告模板；不改业务代码。正式漏洞报告等敏感内容的"允许进入打包"清单由维护者逐项批准。

## Evidence and evaluation
- AC-01：allowlist 外任何文件不可进入包（越界即失败）；缺件清单准确（缺哪项、阻塞什么一目了然）。
- AC-02：命名、≤10MB、敏感信息扫描、SHA-256 清单、离线校验全部有记录；扫描零命中也要记录扫描范围。
- AC-03：模拟上传→下载→打开复核一轮完成并留档（10-21）。

## Security and operational risks
未过披露审核的漏洞材料（PoC/利用细节）严禁进入提交包之外再漏进公开仓库——打包 allowlist 由维护者逐项批准。报名字段含个人信息，走本地配置不提交。关联 #288/#290、E08/E11、正式材料清单（冲刺计划 §4）。
