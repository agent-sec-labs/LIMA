## 3 应优先实现的功能

### P0 全仓分批扫描和覆盖账本

`lima/repository_scanner.py:698–702` 将排序后的 C/C++ 源文件直接截到 `MAX_UAF_TRANSLATION_UNITS`；该常量在 `lima/cxx_memory.py:158` 为 16。`run_platform_review` 的未审阅记录无法自行知道入口未传入的剩余源文件。这限制的是常规入口的智能体分析范围，不等于所有静态工具都只扫描 16 个文件。

应在调度层保留 16 TU 的单请求预算，分批覆盖完整目标集合。保存总 TU、入选/已审阅/未审阅/失败/预算耗尽数量及逐项原因，支持中断恢复。快照文件和字节读取覆盖率不能替代语义审阅覆盖率。

`run_platform_review` 已有并行和缓存参数，但常规扫描调用未传 `parallelism` 或 `cache`；`LIMA_CXX_AGENT_PARALLELISM` 已定义，却未接入该服务链。`detect_changed_files` 目前是工具函数，未形成常规扫描的增量重跑流程。

验收：超过 16 TU 的目标不能被静默裁掉；不同批次结果可聚合，失败和未处理范围可见；并行配置实际生效；缓存/增量不得跨构建配置错误复用。

### P0 合法且有判别性的 PoC 验证

已有真实 ASan 工作台；`lima/openharmony_validation.py` 已做漏洞版/修复版各三次回放，不能再将其列为完全缺失。缺口是推广到每条正式漏洞，并验证 API 使用和触发链是否合法。

最新台账 `docs/COMPETITION_VALIDATION.md:251–254` 记录：r17 的驱动在 handler 内重置解析器，r18 则先释放句柄再调用 API，造成修复版也崩溃。当前 `experiment_matches_target` 校验运行阶段、错误族及目标文件归因；这些条件无法独自排除落在库源码内部的驱动非法用法。

应补充 PoC 的输入可控性、API 前置条件、句柄生命周期、线程/回调约束和真实入口依据。已知漏洞使用同驱动双版本对照；新漏洞使用维护者确认的根因修复/反事实对照及真实调用路径。驱动非法、桩改变关键语义或仅人为制造崩溃时，不得进入正式漏洞清单。

验收：每条正式漏洞有独立 PoC、真实编译/执行记录、重复结果和负对照；环境失败与 clean 分开；不能仅凭 runtime-confirmed 标签宣称可提交。

### P0 OpenHarmony 构建上下文和真实案例

当前案例由管理员预置 checkout、compdb 和 overlay。已存在 BuildRecipe/ContextPackage 基础，但 `deploy/build-recipes/` 只有 ResInsight 配方；未见接通常规扫描的 OpenHarmony 专用 GN/Ninja/产品配置构建流程。

应先选定受支持的 OH 组件和产品配置，导出真实宏、生成头、跨仓依赖及链接闭包，绑定组件 commit 与构建配置身份。现有平台自动实验调用只提交目标 TU，复杂跨文件链接仍依赖桩或人工准备。跨组件源码清单与分批任务是实现大规模目标的建议方案；赛题并没有逐字要求自动联网下载所有仓库。

尤其要替换或补充参赛阳性案例：`evaluation_data/openharmony/README.md` 明确说明 OH 的 expat 构建未启用 `XML_DTD`，现 pilot 是“OH 生态同源上游组件”验证。不能将添加该宏后的触发作为 OH 实际构建受影响证明。

验收：至少一条在所选 OH 版本和真实配置中可达的安全漏洞，完整保存来源、构建、合法 PoC、影响和修复材料。未知范围须标 unknown。

### P0 Release/LTS 分支影响矩阵

`lima/impact_mining.py` 已实现 blame、branch/tag contains；`scripts/check_finding_on_branches.py` 已提供文件相同/变化/缺失/错误分类。它们提供排查线索，不能独自判定漏洞影响。

### P0 正式报告完整性门禁及入口接线

已有 `agent_report.py` 和 `write_validation_bundle`，不能重新开发一套报告系统。需要将常规扫描结果接到正式漏洞档案与可独立下载的证据包，并区分候选附录和正式漏洞清单。

目前 dossier 允许无 PoC、未提供版本、缺省修复建议；常规 Finding 投影还会将 C++ 结果统一为 HIGH、`fix=""`（`repository_scanner.py:300–311`）。报告侧 `_compile_commands` 使用固定模板，没有真实 compdb 宏/include/语言切换等参数，复杂案例不能据此直接复现。

应增加发布前检查：源码位置及快照片段、CWE/可核实 CVE、合法触发条件、完整 PoC、实际环境与编译命令、运行证据、代码/功能模块、版本矩阵、具体修复建议。缺项明确阻止进入正式清单，同时保留候选研究记录。源码/PoC 等超过 UI 预算时通过独立 artifact 交付，不能静默丢弃。

### P0 性能采集与真实评测入口

补充墙钟、进程树和 Sidecar 内存/CPU采样、资源限额、工具/模型身份、文件/TU/字节规模及实际覆盖。已存在历史耗时，缺本次运行可归属的峰值内存等证据。采样峰值与容器生命周期峰值须区分。

## 4 应继续补齐的分析能力

### P1 危害判定和严重度

建立攻击者输入→真实入口→错误操作→安全后果的证据链。将纯算术溢出、普通空指针崩溃、功能错误和无安全价值 DoS 排除或转入待复核。CWE-190 需证明溢出影响分配大小、索引或访问长度，并核对可控性和可达性；封闭 CWE 词表不能替代这一判据。

`agent_report.py:68` 按证据状态映射高/中/低危，常规 Finding 又统一 HIGH。应分开表达“是否证明成立”与“成立后危害多大”，基于攻击面、权限、可控性和机密性/完整性/可用性评估风险。赛题要求严重程度，未强制 CVSS；可采用可解释评级并可选输出 CVSS。

### P1 CWE 动态判读与类型扩展

内存包已经声明 CWE-416/415/787/125/476/190 六类，不能写成只有四类。可是 `cxx_analyzer/repro.py:51–52` 当前只开启 ASan，解析器处理 ASan 报告；CWE-190 在包内依赖 UBSan 风格标记，尚缺对应插桩和诊断解析链。

需补 UBSan 编译/解析/归因以及整数溢出到内存影响验证；CWE-787/125 的最终分类需使用 READ/WRITE 等证据，而非共用 buffer-overflow 字符串就确定读写方向。随后按真实样本补信息泄露、鉴权/权限提升和安全逻辑漏洞包及相应 Oracle。类型多样性是加分方向，不能只靠增加 CWE 枚举宣称覆盖。

### P1 CVE 知识维护

现有离线三键匹配器可复用。需要维护 OH 官方通告与上游组件映射、版本/commit 关系和证据来源，区分“关联候选”与“归因已验证”。未命中索引只说明当前索引无对应项，不能直接断言新漏洞。

### P1 修复建议和补丁回归接线

`ReproWorkbench.run_patch_regression` 已存在，但未见常规平台检测流程调用；pilot 的已知补丁和同 PoC 双版本回放已有实现。应为正式漏洞输出针对根因的建议；提供补丁时保存最小 diff，并以同 PoC验证原版触发、补丁版不触发及正常功能回归。

自动生成补丁不是满足赛题的前提；已有 avrcp 人工所有权修复和回放可作为证据来源，但台账仍标明未完成正常业务回归及真机/模拟器验证。
