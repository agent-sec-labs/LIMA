# LIMA C++ UAF v2 通俗说明

这份文档用简单例子解释 UAF v2。它方便讨论和理解，不替代正式技术合同。

正式开发和验收仍以
[`2026-09-10-cxx-uaf-v2-design.md`](./2026-09-10-cxx-uaf-v2-design.md)
为准。如果两份文档的表述有冲突，以正式技术版为准。

## 一句话说明

LIMA 先让 Clang 从代码里找出确定的事实，再用固定规则判断是否存在释放后使用。只有固定
规则无法回答时，才让大模型帮忙分析。

这和旧流程最大的区别是：大模型不再负责给漏洞定案。

## 先看一个最简单的 UAF

```cpp
#include <iostream>

int main() {
    int *p = new int(7);
    int *q = p;
    delete p;
    std::cout << *q;
    return 0;
}
```

这段代码做了四件事：

1. `new int(7)` 创建了一个对象。
2. `p` 和 `q` 都指向这个对象。
3. `delete p` 释放了这个对象。
4. `*q` 又访问了已经释放的对象。

所以问题不在于变量名是 `p` 还是 `q`。真正要跟踪的是它们背后的同一个对象。

UAF v2 就是围绕这个对象工作。

## 完整流程

```text
读取代码快照
    ↓
找到真实编译参数
    ↓
Clang 提取对象、指针、释放、访问和控制流事实
    ↓
生成 UAF 候选
    ↓
执行七项固定检查
    ├─ 全部通过：确认静态事实，直接报告
    ├─ 明确不成立：拒绝这个候选
    └─ 无法判断：交给 Lifetime Specialist 和 Critic 分析
    ↓
关联 Semgrep、Clang Static Analyzer 和 ASan 证据
    ↓
由固定规则生成最终结果
```

下面按这个顺序解释。

## 第一步：固定本次分析的代码

LIMA 先为仓库生成一个只读快照，并计算快照哈希。

后续看到的源码、Clang 事实、工具报告和大模型引用都必须属于这个快照。这样可以避免一种
常见错误：分析开始后代码变了，最后却把旧证据和新代码混在一起。

快照哈希可以理解成这份代码的指纹。

## 第二步：找到正确的编译方式

C++ 代码不能只看文件内容。头文件路径、宏和 C++ 标准不同，Clang 看到的程序也可能不同。

例如：

```cpp
#ifdef FEATURE_X
delete p;
#endif
```

如果没有正确的宏定义，Clang 可能根本看不到 `delete p`。

因此 LIMA 会先查找仓库已有的 `compile_commands.json`。它记录每个源文件实际使用的编译
参数，包括：

- 头文件路径；
- 宏定义；
- C++17、C++20 等语言标准；
- 编译目录和目标参数。

如果找不到可靠的编译信息，LIMA 可以用最基本的参数尝试解析，但这时只能说“上下文不完整”，
不能把结果升级为静态确认。

### 为什么默认不运行 CMake

待扫描的仓库可能不可信。`CMakeLists.txt` 可以启动其他程序或写文件，所以 LIMA 默认只读取
已有的 `compile_commands.json`，不会为了生成它而执行 CMake 或其他构建脚本。

管理员可以为可信仓库单独开启构建上下文生成。即使开启，也必须在无外网、非 root、源码只读、
资源受限的临时隔离环境中运行。隔离条件不完整时，LIMA 不执行构建脚本。

## 第三步：让 Clang 提取事实

Clang 不直接输出“这是漏洞”。它先输出程序里实际发生了什么。

对于前面的示例，LIMA 需要得到类似下面的事实：

```text
F1：在 main 中创建对象 O1
F2：p 指向 O1
F3：q 从 p 获得指向关系，所以 q 也指向 O1
F4：delete p 释放 O1
F5：*q 访问 O1
F6：控制流可以从 F4 走到 F5
```

每条事实都保存源码位置、所属函数、Clang 版本、编译参数哈希和快照哈希。

这一步只相信 Clang 能明确提取的内容。遇到宏、模板、跨函数所有权、复杂指针转换或不完整
控制流时，LIMA 会记录“这里没有分析完整”，不会自行猜测。

## 第四步：生成候选

如果同一个对象同时出现“释放”和“释放后的访问”，LIMA 就生成一个 UAF 候选。

候选不是漏洞结论。它只是告诉下一步：请检查对象 O1 的这一次释放和这一次访问。

候选身份由对象、释放位置和访问位置确定。模型不能修改这些内容。

系统内部还会把快照哈希和候选编号一起使用：

```text
(snapshot_hash, candidate_id)
```

单独的 `candidate_id` 不能用来查询缓存或绑定工具证据。这样可以防止两个不同版本的仓库碰巧
产生相同候选编号后，错误复用旧证据。

## 第五步：执行七项检查

Proof Engine 会回答七个固定问题。

| 编号 | 要回答的问题 | 示例中的答案 |
|---|---|---|
| P1 | 这个对象真的被创建了吗？ | 是，`new int(7)` 创建了 O1 |
| P2 | 使用时的指针还指向这个对象吗？ | 是，`q` 通过 `q = p` 指向 O1 |
| P3 | 这个对象被释放了吗？ | 是，`delete p` 释放了 O1 |
| P4 | 释放后又访问对象了吗？ | 是，代码执行了 `*q` |
| P5 | 程序能从释放位置走到访问位置吗？ | 是，两行顺序执行 |
| P6 | 中途有没有让 `q` 改指向新对象？ | 没有 |
| P7 | 中途有没有重新开始这个内存位置的生命周期？ | 没有 |

每一项只有三种结果：

```text
satisfied：已经证明这项条件成立
refuted：已经证明这项条件不成立
unknown：现有分析无法可靠回答
```

最终规则很简单：

```text
七项全部 satisfied
并且编译上下文和代码覆盖完整
→ PASS

任何一项 refuted
→ REFUTED

剩下的情况
→ UNKNOWN
```

### P5 为什么要谨慎

在控制流图中能从 A 走到 B，不代表真实输入一定能走通这条路径。

```cpp
if (x > 10)
    delete p;

if (x <= 10)
    std::cout << *p;
```

从代码结构上看，`delete` 在 `use` 前面。但是同一个 `x` 不可能同时满足这两个条件。

第一阶段不加入复杂的数学约束求解。P5 会分开记录：

- 结构上是否可达；
- 条件是否确定可行。

直线执行和同一个简单分支内的释放后访问可以通过。需要比较多个条件、分析循环或推导变量
关系时，条件可行性记为 `unknown`，P5 也就是 `unknown`。

## 三种 Proof 结果会怎样处理

### PASS

前面的简单示例会得到 PASS。LIMA 直接输出：

```text
verification_state = fact-verified
evidence_level = D2
```

这里的 D2 表示静态分析已经形成完整证据链。这个过程不需要调用大模型，也不要求 Semgrep、
Clang Static Analyzer 或 ASan 同时报错。

### REFUTED

下面的代码在释放后让 `q` 指向了新对象：

```cpp
int *p = new int(7);
int *q = p;
delete p;
q = new int(9);
std::cout << *q;
```

P6 会被反驳，因为实际访问的是新对象。候选被拒绝，不再调用大模型。

其他常见反例包括：

- 释放路径和访问路径不可能同时执行；
- 访问前重新开始了对象生命周期；
- 使用的指针实际指向另一个对象。

### UNKNOWN

如果关键关系跨函数、控制流太复杂或编译上下文不完整，Proof Engine 返回 UNKNOWN。

这不等于“代码安全”，也不等于“已经发现漏洞”。它只表示固定分析目前回答不了。

## 第六步：只有 UNKNOWN 才询问大模型

UNKNOWN 候选最多经过两个模型角色：

1. Lifetime Specialist 检查对象、别名、释放和访问关系。
2. Critic 专门寻找反例，比如重新绑定、不可达路径或遗漏的安全条件。

两个角色都只能引用已有候选和事实编号。它们不能新增 Clang 事实，也不能把 UNKNOWN 改成
确定性 PASS。

即使两个角色意见一致，结果最高也是：

```text
semantic-supported
evidence_level = D1
```

D1 结果会出现在报告里，但默认不阻断 CI。如果模型仍然无法排除关键疑问，结果就是
`needs-human-review` 或放弃报告。

## 第七步：关联其他工具证据

LIMA 还会尝试关联 Semgrep、Clang Static Analyzer 和 ASan 的结果。

Evidence Broker 只输出三种关系：

| 结果 | 含义 |
|---|---|
| `support` | 工具对同一快照中的同一候选提供了正向证据 |
| `contradict` | 工具提供了明确、可追溯的反证 |
| `no-evidence` | 工具没运行、没报、没覆盖相关路径，或者无法准确绑定 |

最容易误解的是 `no-evidence`。

如果 Clang Static Analyzer 没报，不能说明代码安全。ASan 跑完没有崩溃，也可能只是测试没有
执行到那条路径。这些情况都是 `no-evidence`，不会推翻已经完成的静态 Proof。

只有工具真的针对同一 `(snapshot_hash, candidate_id)` 给出明确反证时，才算
`contradict`。如果它和确定性 Proof 冲突，LIMA 会保留双方证据并要求人工复核。

## 证据强度和证据方向是两件事

每条证据分别记录“有多强”和“支持哪一边”。

```text
level：D0、D1、D2、D3 或 D4
polarity：SUPPORTS 或 REFUTES
```

例如：

```text
七项 Proof 全部通过：D2 + SUPPORTS
确定性证明中途发生 rebind：D2 + REFUTES
ASan 真实复现同一 UAF：D3 + SUPPORTS
```

不能因为证据是 D2 就默认它支持漏洞。D2 也可以是一条很强的安全反证。

## 大模型运行模式

UAF v2 继续使用 `off`、`auto` 和 `required` 三种模式，但它们只影响 UNKNOWN 分支。

| 模式 | PASS 或 REFUTED | UNKNOWN |
|---|---|---|
| `off` | 正常完成，不调用模型 | 不调用模型，保留为未确认 |
| `auto` | 正常完成，不调用模型 | 尝试调用模型，失败后降级 |
| `required` | 正常完成，不调用模型 | 模型必须成功，否则任务失败 |

所以 `required` 不表示每个候选都必须调用模型。简单 UAF 已经被固定规则证明，不再浪费一次
模型调用。

## 第一阶段能处理什么

第一阶段只承诺处理一个比较小但能做扎实的范围：

- `new/delete`；
- `malloc/free`；
- 释放后执行 `*p`；
- 释放后执行 `p->member`；
- 同一函数、同一编译单元；
- 简单的局部指针复制，例如 `q = p`；
- 直线流程和能够明确判断的简单分支。

下面这些暂时不会被升级为 `fact-verified`：

- 跨函数或跨文件的所有权传递；
- 模板和关键宏展开；
- 容器、成员字段、回调或全局变量保存的别名；
- 复杂分支、循环、异常和异步流程；
- 并发；
- 自定义内存分配器；
- 缺少可靠编译参数的项目。

暂不支持不代表它们安全。LIMA 会把这类情况标成 UNKNOWN 或 coverage 不完整。

## 其他 CWE 会怎样

这次只替换 CWE-416 的检测流程。

CWE-415、CWE-125 和 CWE-787 继续走现在的流程。唯一共用的变化是安全设置：面对不可信仓库，
LIMA 不再默认执行它的构建脚本。

## 实现顺序

开发会按下面的顺序进行：

1. 先处理泄露凭据和默认自动运行构建脚本的问题，并重新记录测试基线。
2. 定义 UAF 事实、候选、Proof 和复合身份的数据格式。
3. 完成编译上下文解析和 Clang 事实提取。
4. 完成候选生成与七项固定检查，先跑通 `new → alias → delete → *p`。
5. 用 rebind、不可达路径和 lifetime restart 三类安全样例压住误报。
6. 接入 UNKNOWN 专用的大模型分析和三态 Evidence Broker。
7. 接入现有扫描入口、报告、API 和前端。
8. 运行 vulnerable/fixed 配对评测，并确认其他 CWE 没有语义回归。

每一步先写会失败的测试，再实现对应功能。不会一次把整条流程全部改完。

## 怎么判断第一阶段做完了

至少要满足这些结果：

- 简单 UAF 不调用大模型也能得到 `fact-verified`；
- rebind、不可达路径和 lifetime restart 不会被误报成已确认漏洞；
- 编译参数不完整时不能得到 `fact-verified`；
- 复杂情况会停在 UNKNOWN，不会靠模型投票升级；
- 外部工具没报时不会被解释成安全；
- 不同代码快照之间不会复用候选证据；
- 待审计仓库默认不会执行 CMake 或其他构建脚本；
- 报告会显示七项检查、代码路径、覆盖缺口和真实模型调用次数；
- CWE-415、CWE-125、CWE-787 的检测逻辑保持原样；
- 所有 C/C++ 结果仍然只检测，不自动修改代码。

做到这些以后，LIMA 就有了一条范围有限但可以审计的 UAF 检测链。跨函数、模板、复杂条件和
并发 UAF 留到后续阶段处理。
